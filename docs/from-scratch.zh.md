# 从零理解我们的 FlashKDA 项目

> 本文是课程入门讲义的公开整理版。公式、数字与结论保持原样；原始日志、答辩 PPT 与实验机二进制未随仓库发布。


这份讲解面向第一次接触 HPC、CUDA 和注意力 kernel 的读者。先解释程序算什么，再解释 GPU 怎样执行它，最后把每次实验放回“为什么要做”的位置。具体数字以 [report.zh.md](report.zh.md) 和 [证据说明](evidence.md) 的证据范围为准。

建议分三次读：第一次读第1—5节，建立计算和硬件概念；第二次读第6—10节，理解实验与优化；第三次读第11—13节，准备答辩。无需先掌握全部 CUDA 语法。

## 1. 我们优化的是哪一层

可以把模型的运行分成几个层次：一段文字被表示成数字张量；模型的一层对这些张量做运算；框架调用算子；算子最终由 GPU kernel 执行。

本项目聚焦其中一个算子的 forward：**KDA，即 Kimi Delta Attention**。我们使用已有算法和已有 FlashKDA 实现，研究怎样让相同计算更适合 B300。我们没有训练一个新模型，也没有修改整套语言模型。

“Flash”可以先理解为该算法的一种高效实现。数学上等价的表达式，放到 GPU 上可以有完全不同的速度。例如把中间矩阵写入显存再读回来，和让它一直留在寄存器中，算出的目标相同，数据搬运成本却不同。

HPC 在这里关心的就是这些具体问题：工作能否分给更多执行单元，数据放在哪里，谁在等待谁，数值精度是否仍符合要求。

我们的任务分三层：

| 层次 | 做了什么 | 为什么要做 |
|---|---|---|
| Task 1 | 跑通原 FlashKDA，记录性能和真实指令 | 建立可靠的比较起点，确认自己正在研究什么 |
| Task 2 | 分别检验 CHUNK、tcgen05、并行度、瓶颈和精度 | 把“也许会更快”拆成可以验证的问题 |
| Task 3 | 分别实现 A：真实Phase6换指令、B：大chunk与rescale、C：value列分片，并对拍和计时 | 分清新指令、数值重写、任务分配各自带来的收益与代价 |

贯穿三层的习惯是：把猜想、离线推导和 GPU 观测分开记录。README 保留过程，report 提炼结论，PPT帮助口头表达。

## 2. 先看输入里的三个数字

主形状是 `[8192,96,128]`，这里可以先读成：

| 符号 | 数字 | 直观含义 |
|---|---:|---|
| T | 8192 | 一次处理8192个token位置 |
| H | 96 | 每个位置有96个head，各有自己的状态 |
| D | 128 | 每个head的向量长度是128 |

token是模型处理的位置单位，并不保证恰好等于一个汉字。head可暂时理解为模型内部并行使用的一套独立向量和记忆；这不意味着我们知道每个head一定对应某个可命名的语言功能。

本项目 key 和 value 的维度恰好都为128，所以常统称D。分析列分片时必须重新区分它们：K是key维度，V是value维度。两个维度长度一样，不代表它们可以用同一种方法切分。

fixed表示一条固定长度序列。varlen表示把多条不同长度的序列放进同一批张量，并用边界信息告诉kernel在哪里重新开始一条独立递推。例如varlen6总token仍是8192，但包含6条独立序列，因此K2可同时处理的状态链更多。

题目还要求注意每卡head数。96个head按TP8分配时，每卡形状可对应12个head。我们实际做的是单张B300上的H12形状实验，未执行八卡通信。

## 3. KDA怎样保存和修改记忆

### 3.1 q、k、v和state分别是什么

每个token、每个head有三个向量：query $q$ 用于读取，key $k$ 用于定位更新方向，value $v$ 是本次想写入的信息。它们由模型前面的计算产生；我们的kernel接收这些数字，执行KDA更新。

每个head还保存一张状态矩阵 $S$。数学上用 $K\times V$ 表示：在本项目中是128×128，共16384个数。它是对过去信息的压缩表示，长度不会随token数不断变成一张T×T表。

KDA不是简单地把所有value相加。它先根据旧状态预测当前value，再写入“真实value与预测value之间的差”。这就是这里的delta更新思想。

### 3.2 用2×2的小例子手算

为了看懂更新，把维度临时缩小到K=V=2。此例忽略遗忘，令写入强度β=1，query已经吸收缩放。初态为零：

$$
S_0=\begin{bmatrix}0&0\\0&0\end{bmatrix}.
$$

第一个token给出 $k_1=(1,0)^\top$、$v_1=(2,3)^\top$。旧状态的预测为 $k_1^\top S_0=(0,0)$，所以要写入的差是 $(2,3)$。外积更新后：

$$
S_1=S_0+k_1(v_1-S_0^\top k_1)^\top
=\begin{bmatrix}2&3\\0&0\end{bmatrix}.
$$

这里所有向量都按列向量记，$S^\top k$ 给出V维预测，$k\Delta v^\top$ 是K×V的外积。

第二个token仍有 $k_2=(1,0)^\top$，但value改为 $(4,1)^\top$。旧预测为 $(2,3)$，差为 $(2,-2)$，所以：

$$
S_2=\begin{bmatrix}2&3\\0&0\end{bmatrix}
+\begin{bmatrix}2&-2\\0&0\end{bmatrix}
=\begin{bmatrix}4&1\\0&0\end{bmatrix}.
$$

同一key方向上的内容被修正到新的value。若β=0.5，则只写一半差，第一行从 $(2,3)$ 变为 $(3,2)$。β可以理解为本次修正强度。

读取时，若query为 $(1,0)$，输出是状态第一行；若query为 $(0,1)$，输出是第二行。真实query/key通常不是这么简单的坐标轴，而是一般的128维向量。

### 3.3 遗忘门控做什么

在写入之前，KDA还会衰减旧状态。这里用已激活的log gate $g_t$ 表示，逐key维度的衰减因子为 $\exp(g_t)$。可先想象所有因子都是0.9，那么旧状态先乘0.9，然后再进行预测与delta更新。

这样，状态可以逐渐忘记旧内容，也可以在某些方向上保留更长的记忆。注意接口传入的raw gate还需要激活，不能直接当成这里的 $g_t$。

用列向量记法，完整公式为：

$$
\bar S_t=\operatorname{diag}(\exp(g_t))S_{t-1},
\qquad \Delta v_t=v_t-\bar S_t^\top k_t,
$$

$$
S_t=\bar S_t+\beta_tk_t\Delta v_t^\top,
\qquad o_t=S_t^\top q_t.
$$

最后输出是V维列向量。若写成 $q_t^\top S_t$，得到的是同一输出的行向量表示。代码还包含q/k归一化和query缩放，读算法时应区分数学输入与接口raw输入。

### 3.4 状态的好处也是并行的限制

处理第2个token需要第1个token的状态。你不能让两个完全独立的工人分别从零计算这两个token，再把结果随意拼接。

不同head的状态则是独立的；不同序列也独立。这些维度可以直接分给不同GPU任务。优化的第一件事，是找出真正独立的工作，而不是先把线程数调大。

## 4. GPU怎样执行这些工作

### 4.1 线程、warp、CTA和SM

| 名称 | 在本项目中怎样理解 |
|---|---|
| thread | 执行kernel代码的一个线程，使用自己的寄存器和索引 |
| warp | 32个线程组成的执行分组，协作执行SIMT和warp级MMA |
| CTA / block | 一组warp，共享一块shared memory，能在组内同步 |
| grid | 一次kernel启动的全部CTA |
| SM | GPU上的执行单元，调度驻留warp并提供寄存器/shared memory等资源 |

B300这次报告了148个SM。可以用“148个工作车间”帮助理解，但这个比喻有边界：一个SM往往同时驻留多个CTA，warp也不是32个独立按任意指令运行的CPU核心。

原K2在fixed H96只有96个CTA。一份CTA一次运行在一个SM上，96个CTA不足以给148个SM同时各分一份工作。H12只有12份任务，工作分散的空间更大。

### 4.2 数据放在哪里会影响速度

| 存储 | 谁使用 | 在本项目中的角色 |
|---|---|---|
| HBM / device memory | 全GPU可访问的大容量内存 | 输入、输出、全局中间工作区 |
| L2 cache | 多SM共享缓存 | 可能复用两个分片重复读取的共同数据 |
| shared memory / SMEM | CTA内线程协作使用 | tile暂存、TMA搬入、state缓冲 |
| registers | 线程持有 | MMA fragments、逐元素计算、中间结果 |
| TMEM | tcgen05使用的专用Tensor Memory | 新MMA的累加结果及相关数据流 |

“更近”不意味着可以无限使用。每个CTA占用太多shared memory或寄存器，就可能使一个SM只能驻留较少CTA。数据搬运、同步、计算和驻留资源必须一起设计。

TMA可以理解为按tensor布局搬运数据的硬件机制；Tensor Core MMA负责矩阵乘加。搬运工具新、计算指令沿用旧代，并不矛盾。

### 4.3 occupancy是什么

occupancy比较的是SM上活跃warp数与硬件允许的warp数。它有理论上限和实际观测值。

理论occupancy回答：根据block大小、寄存器和shared memory等约束，最多能驻留多少warp？实际achieved occupancy受运行中的工作量、等待与尾部影响。

它不是全GPU速度，也不是所有SM的开工比例。一个任务可能让少数SM内部很忙，其他SM没有工作。另一个任务可能让更多SM各做少一些工作，但总体更早完成。H12的P2恰好给出了这种实测例子。

指标定义以 [Nsight Compute文档](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#metrics-guide) 为准；看任何百分比都要先问它的分母是active cycles还是elapsed cycles。

## 5. FlashKDA为什么分chunk、分两个kernel

逐token直接执行上面的递推，会产生许多小操作和依赖。FlashKDA把16个token放进一个chunk，通过代数重排把块内关系变成更适合GPU的矩阵乘；chunk之间仍通过state顺序连接。

K1先做不依赖传入state的准备，包括gate变换、q/k处理、小矩阵构造与求逆。K1可以按chunk并行，因此fixed H96有 $96\times(8192/16)=49152$ 个CTA。

K2再用这些准备结果处理状态递推和输出。原实现每head一份CTA，它在内部循环512个chunk，因此只有96个CTA。K1任务充足，不代表K2也有足够任务。

我们初次NCU看到K2占两个目标kernel时间约73.3%，grid又小。这是选择优先研究K2的依据。它不意味着后续随便改K2都会成功，只说明改它可能影响更多时间。

阅读源码时可以这样定位：

| 文件 | 先回答的问题 |
|---|---|
| `fwd_launch.cu` | 启动多少CTA？每CTA多少线程？准备多大shared memory？ |
| `fwd_kernel1.cuh` | 每个chunk预先算了哪些数据？ |
| `fwd_kernel2.cuh` | state怎样跨chunk保留？compute/load/store各做什么？ |
| `utils.cuh` | 小矩阵求逆、转换和MMA helper怎样复用？ |

第一次阅读不必从CuTe模板类型逐个字开始。先画出数据和依赖，知道每个buffer代表什么，再看布局如何实现。

## 6. Task 1建立了什么基础

我们先把题目固定版本安装到B300，跑代表性正确性和原benchmark。这一步建立baseline：后续的候选必须和同一来源比较。

然后用NCU导出SASS。可以把CUDA C++理解为程序员写的源代码，PTX理解为编译中间表示，SASS则更接近设备最终执行的指令。我们看到HMMA.16816，与源码SM80 MMA atom对应，从实际代码生成确认研究起点。

静态SASS出现一行指令，不能推导它只执行一次，因为这行可能在循环中反复执行。反过来，同一地址在报告里重复出现，也不意味着硬件多做了同样数量的独立工作。我们因此没有用296行命中计算动态FLOP。

原benchmark提供了三个H96用例的性能基线。它同时打印几种state接口和不同算法。比较时统一口径，避免把较快的一列随意挑出来作为另一个实验的分母。

这体现一个很实用的习惯：在优化之前，先能回答“我测了哪个文件、哪个binary、哪个输入、用哪种计时、结果是否正确”。

## 7. Task 2怎样把大问题拆小

### 7.1 为什么不能直接把CHUNK从16改成64

直觉会说：chunk更大，循环次数更少，应当更快。但每个chunk内部的求逆矩阵也更大，而且累计衰减范围更宽。

指数范围实验单独拿出实际CUDA指数和BF16转换，观察前缀衰减及其逆。这么做是为了定位数值表示风险，避免把复杂完整kernel的NaN全归到某个猜想上。α=5时第18项就出现0/Inf，已经超过C16但落在C32里面。

求逆实验再单独研究16、32、64维严格下三角矩阵。严格下三角矩阵有一个好性质：足够高次幂必为零，Neumann级数在精确算术下有限终止。但计算机在中间每步都舍入，完整答案有限不保证中间部分和可表示。

我们实测到C32某个相干输入的逆全部有限，但相对误差超过300%。这个例子说明“运行结束，没有NaN”只是很低的一层检查。

最后用统一的MMA实现量化求逆成本。C32、C64相对C16批次时间增加7.42×、53.68×，虽然矩阵任务数减少了。这个数字只属于该求逆实现，没有被写成完整KDA的减速倍数。

三步分别回答：会不会先溢出？即使不溢出是否正确？在可计时的输入上成本如何？这样每个结果都有可解释的范围。

### 7.2 新的tcgen05为什么不是改个类型名

MMA是矩阵乘加，常写成 $D=A B+C$。不同代的MMA对tile形状、操作数位置和线程组织有约束。

现有HMMA适合小的m16n8k16片段，而且中间结果已经留在寄存器中，紧接着做beta、转置和下一次乘法。tcgen05的累加结果进入TMEM，后续要读取、转换、同步；如果下个乘法需要SMEM中的B，还要再准备一套数据。

所以“数学上相同”不保证“物理数据流相同”。编译器也不会仅因为运行在B300，就替我们自动设计一个新的TMEM流水线。相关合法形状和存储规则见 [NVIDIA PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#tcgen05-matrix-shape)。

我们选择Phase6，因为它的128×16乘16×128结果较大，适合新tile，而且处于state更新末端，便于划清实验边界。

独立tcgen05原型在32步复用场景下快约1.11×，单步略慢。多步结果与一次性成本得到摊薄的解释相符。这里的A/B指矩阵乘的两个操作数：原型复用它们，没有生成前序阶段的真实U。这个局部实验不能给出完整KDA的性能答案。我们随后真正把Phase6接入完整KDA，称为路线A；第8和10节解释它为何反而变慢。

### 7.3 为什么研究BF16 state精度

BF16用16bit保存一个数。相对FP32，它减少state存储字节，但有效精度较低。FP32累加后写回BF16，还是会发生舍入。

递推会把上一步的state作为下一步输入，因此某次舍入有可能影响后面许多token。强遗忘可能衰减旧误差，弱遗忘和慢写入则值得专门检查。

我们建立一个FP64参考，再做一个只在chunk边界舍入state的Q16模型，最后比较真实FlashKDA。这样可以问：“周期性state舍入是否可能解释观察到的趋势？”而不把所有误差默认归给Tensor Core。

慢写入head最终state误差约3.77%，最后128个token输出误差约3.75%，均未出现非有限值。Q16的趋势相近，但与真实kernel并不完全相同，说明其他近似运算仍有作用。

这是一次诊断，不是语言模型质量验收。真实任务能容忍多大误差，需要实际任务指标和明确标准。本项目没有用NaN检查替代这个标准。

## 8. Task 3：分别改指令、改chunk、改任务分配

三条路线从同一基线出发，各自编译或调用独立实现，没有把三种改动混成一个候选。这样发现差异时，至少知道自己比较的是哪种设计。

### 8.1 路线A：将新MMA接入真实的状态更新

我们的目的，是检验第7.2节的局部机会能否进入完整forward。CHUNK仍是16，K1和K2前五个阶段保持原计算，最后Phase6改用tcgen05。每一步都使用前序计算出的真实U，保持原来的BF16 state舍入边界。

困难在于，旧U已分布在各线程的寄存器里，新乘法需要另一种输入布局。于是先把U写入shared memory、同步并整理矩阵，再发出新MMA；完成后读取TMEM，执行gate乘加并写回BF16 state。这些工作和矩阵乘一起计时。

为什么再做一个 `A_control`？它采用相同的U物化、packed布局和重写的后处理，但乘法继续用HMMA。如果它也很慢，就不能把A的全部回退归给新指令。控制组不能完美分离每个硬件原因，却能让结论比简单的“新旧MMA比速度”更可靠。

两者每CTA的dynamic shared memory都从98432 B增加到110848 B。SASS确认A的完整recurrence中实际有UTCHMMA，其余阶段仍有HMMA。**从SM80到SM100式计算路径，在本项目中是一次真实的数据流改写，不是把编译目标名字换掉。** B300实际使用的目标是 `sm_103a`；它与其他Blackwell目标的二进制兼容性没有在本项目验证。

### 8.2 路线B：先让真正的C32/C64能够稳定地算完

大chunk会把更多token放进同一次块内计算，减少块间循环，但旧指数分解容易产生极小衰减和极大逆衰减。即使两者最后应当抵消，中间已经得到0或Inf就来不及了。

令 $G_i$ 是chunk内的log gate前缀。B直接计算两个位置之间的衰减 $\exp(G_i-G_j)$。对因果位置 $i\ge j$ 和非正gate，差值非正，因此不会生成正指数方向的巨大逆衰减。未来位置先屏蔽再求exp。跨chunk传递真实state，下一个chunk的前缀重新从零开始；这就是这里的相对前缀重标定。

块内关系组成单位下三角方程 $(I+L)U=R$。B使用FP32求解和内部FP32 state，替换原来的低精度显式Neumann求逆。我们真正执行C32/C64完整块，还做同样求解器和精度的B16控制组，以观察改变C本身后的差异。

这是PyTorch CUDA组合实现：多个张量操作、求解器和矩阵乘共同完成forward。它具有正确完整的KDA计算，但尚未做成像原FlashKDA那样的融合kernel。单个 `[H,C,C,D]` FP32临时数组，在H96/D128时随C16/32/64增为12/48/192 MiB。循环变少与中间数组变大同时发生，必须测量实际权衡。

精度改善也要谨慎解释：rescale、FP32求解、FP32 state和激活实现一起变化，不能把所有改善只归给rescale。

### 8.3 路线C：从公式判断value列能否独立计算

回看 $\Delta v=v-S^\top k$。对某一个value维度j：

$$
\Delta v_j=v_j-\sum_{i=1}^{K}k_i\bar S_{i,j}.
$$

计算第j个value只使用state的第j列。更新也只修改这列：

$$
S'_{i,j}=\bar S_{i,j}+\beta k_i\Delta v_j.
$$

列j不需要读取列j+1的新结果。由此可以把128列分成前64列和后64列，每组独立完成全时间递推，最后各自写出属于自己的输出。

为什么不直接拆key维度？因为上式对i有求和。把key拆成两半后，需要合并两个部分内积；如果没有归约，得到的就不是同一计算。这是区分两个128维轴的重要原因。

### 8.4 数学列和内存行怎么对应

数学上我们写S为 `[key,value]`，所以拆value是拆列。实际CUDA存储采用 `[value,key]`，同一个操作在内存中表现为拆出两块64×128区域。

因此我们同时改了tile、TMA descriptor、地址偏移和矩形state转换。只改grid、不改这些布局，会让两个CTA写重叠数据或读错区域。

离线地址检查验证每个输出/state元素的归属唯一，代数检查验证列独立。但GPU中的CuTe布局、TMA行为仍要实机对拍，这就是后续正确性实验的必要性。

### 8.5 更多CTA带来什么代价

baseline每head一个CTA，4个compute warp处理128列，另有1个load warp和1个store warp。P2每head两个CTA，每个2个compute warp处理64列，也各自需要load/store角色。

因此总compute warp保持4个，但I/O角色从2个变为4个。每个分片还需要共同的q/k/gate、小矩阵等输入。它们不能凭分片消失，可能被重复读入。

P2把每CTA的dynamic shared memory从98432B降到68608B，约少30.3%。单SM的shared-memory block limit从2变3，但warp/CTA也从6变4，理论warp数仍为12。这就是我们没有提前承诺occupancy一定提高的原因。

## 9. 如何确认优化没有算错

我们把检查分成三个问题：候选是否保持预定计算？它相对独立数学参考的误差多大？被计时的Graph是否真的执行并写出了结果？

最新统一full对拍中，A_control、A、B16、B32、B64、C各有38个用例。包含fixed/varlen、七种state接口、batch2、不同尾长、强弱gate、零或同向q/k、H12/H96，以及四个T8192主形状和弱遗忘长链。六个实现合计420项output/state检查、228项初态记录均通过；空初态的“不变”检查按不适用处理，不冒称检查了228个非空初态。

| 检查对象 | 本次结果 | 它说明什么 |
|---|---|---|
| A_control、A、C与baseline | 已测output/state逐位一致 | 改写没有增加已测输入上的数值差异 |
| 所有实现与题目FLA naive | 通过各自预定门槛 | 与独立参考联系起来，同时保留原BF16误差范围 |
| B16/32/64 | NRMSE≤0.5%，max_abs≤0.01 | 当前FP32组合实现符合本次工程标准 |
| 计时后Graph写出 | 96项检查通过 | 填NaN后重放能恢复正确结果，初态保持不变 |

NRMSE在这里是误差向量的二范数除以参考向量的二范数：可以先理解为总体相对误差。max_abs检查最大的单元素绝对偏差，避免平均指标掩盖局部异常。

A/C使用与baseline误差关联的FLA验收范围，详细公式在report第5.4节，不能把它们写成“相对FLA零误差”。在新的 `weak_long` 用例中，baseline/A/C末状态NRMSE约3.61%，B约0.167%。这与第7.3节的历史FP64探针是不同输入与参考，不能将3.61%与3.77%直接当成一次优化的前后值。模型任务是否接受这些误差，还需要任务质量指标。

性能计时前检查eager与Graph一致，计时后把输出和终态填NaN再重放。检查通过才接受COMPARISON，避免图没有真正写出却拿旧结果计时。旧P2的17用例和先前失败都保留在README，新full检查是在其基础上扩展。

Ninja PATH错误发生在编译之前，不是kernel算错。我们先做只读诊断，确认包存在但可执行文件不在PATH，再修复构建入口。把失败分层归类，能避免无谓修改CUDA代码。

## 10. 三条路线的结果怎样解释

### 10.1 先看完整性能，不从单个指标猜

先看路线C。最新运行统一BF16 state接口、完整forward，每图一次调用，12轮交替顺序，取中位数：

| 用例 | 配对baseline | C（原P2） | 结果 |
|---|---:|---:|---|
| fixed H96 | 1.028480 ms | 1.162928 ms | 时间增加13.07% |
| varlen6 H96 | 0.859712 ms | 0.984272 ms | 时间增加14.49% |
| varlen8 H96 | 0.689776 ms | 0.790000 ms | 时间增加14.53% |
| fixed H12 | 0.791984 ms | 0.685872 ms | 时间减少13.40%，加速1.1547× |

加速倍数是旧时间除以新时间。1.1547×意味着约15.47%的速度比提升，对应时间减少13.40%；不要把两者混成一个百分比。

这些是单GPU内完整forward的图执行时间，不包括CPU提交、图外分配和模型其他层。不能据此说整模型快了13.40%。旧P2实验是每图20次调用，输入和预热也不同，保留为历史结果，不与新数值直接相除。

### 10.2 NCU帮助定位差异

本节采用此前对同一C二进制的NCU实验（README第36节）。它支持C的机制分析，没有测量新增A/B，且不是最新Graph计时的同一采集条件。

NCU对照中K1几乎不变，主要变化位于K2，符合修改范围。H12的K2任务从12变24，平均SM active/elapsed周期比从8.02%变16.06%。即使每个活跃SM内warp较少，更多SM获得任务，整体可以更早结束。

H96从96变192个CTA，也扩大覆盖，但eligible warp和issue active下降，共同输入重复读取的成本更明显。按同一kernel的DRAM带宽乘duration估计，H96的数据总量增加约26.9%，H12仅约2.15%；缓存命中表现也不同。

这些变化共同支持：H12严重缺少独立任务，拆分收益较大；H96中额外I/O和局部发射效率损失更占上风。我们没有做逐项消融，所以没有把某个百分比精确归因于单一硬件事件。

### 10.3 三个看似反常的现象

**数据读得更快，但总时间更长。** 带宽是每秒传多少字节。如果传输总量增加得更多，带宽提高仍可能耗时更长。H96正需要同时看总量和duration。

**occupancy降低，但kernel更快。** occupancy关心SM内部warp驻留；增加全GPU的工作覆盖可以带来更大收益。H12不能只看9.37%变6.25%就判失败。

**shared memory减少，但理论occupancy不变。** block limit从2变3，同时warp/CTA从6变4，乘积仍为12。这是资源表必须结合block大小解释的例子。

### 10.4 为什么A和B没有得到正收益

对fixed H96，A的配对baseline约1.0302 ms；A_control为2.7222 ms，A为2.9145 ms。保留HMMA的控制组就已明显变慢，说明共同引入的U物化、布局、同步和后处理改写不能忽略。A再比控制组慢7.06%；四个形状的额外回退为7.06%—20.69%。我们没有对每个成本单独消融，因此不能把差值称为纯MMA指令延迟。

局部原型快、完整A慢并不矛盾：原型复用准备好的操作数，完整实现每个chunk必须接收真实U并交给下一步state。局部实验发现机会，完整实验决定当前集成值不值得启用。**本次A已经实际集成和对拍，结果是该版实现不值得替换baseline。**

| B的完整forward | B16控制组 | B32 | B64 |
|---|---:|---:|---:|
| fixed H96 | 99.0414 ms | 120.4751 ms | 199.1444 ms |
| fixed H12 | 46.0817 ms | 32.8325 ms | 35.5712 ms |

它们的配对FlashKDA基线约0.79—1.03 ms。因此，B虽然正确性通过，当前组合实现仍远慢于融合基线。B32在H12比B16快28.75%，但H96约慢21.64%；说明更大chunk确实改变循环与中间数组之间的权衡，却没有抵消整个组合实现的成本。

这里的结论属于本版FP32组合算法，不能推广成“所有大chunk融合SM100实现都慢”。下一轮工程优化若需要展开，应先减少中间张量和kernel边界、设计融合数据流；当前作业的实现、对拍和性能结果已经齐全，无须为掩盖负收益再重复同一实验。

## 11. benchmark、microbench和profiler怎样分工

| 工具或实验 | 回答的问题 | 容易误用的地方 |
|---|---|---|
| 官方benchmark | 原实现相对既定参考有多快 | 不同state接口、不同算法或mean口径混用 |
| microbench | 单个数值或实现机制是否可行、成本如何 | 局部1.11×当成全kernel1.11× |
| CUDA Graph完整forward | 同一接口下baseline与候选的GPU执行时间 | 误称包含CPU API或服务延迟 |
| NCU | 哪个kernel、资源或执行指标发生变化 | profiling replay时间替代正常benchmark |
| SASS | 编译出了哪些硬件指令 | 静态行数当作动态执行次数 |
| SHA-256 | 回传与归档是否对应同一文件字节 | 有hash就假装拿到了远端binary内容 |

CUDA调用通常是异步的。CPU把工作提交出去就能继续走，因此单纯给Python调用前后加CPU秒表，可能只量到提交开销。CUDA Event或Graph事件时间针对GPU执行，但也必须说清事件包住了什么。

预热用来避开首次加载、分配或初始化的影响。交替顺序减少某条路径总是先测造成的偏差。多轮保留原始时间能检查波动；固定一次进程内的12轮也不等于所有机器、所有日期的保证。

NCU为了采集许多指标会重放kernel，缓存控制又与普通计时不同。因此我们用Graph决定是否更快，用NCU解释为什么，两套duration各自保存。

## 12. 答辩时怎样组织“做了什么、为什么做”

可以按以下顺序讲，每个选择都连接到一个已观察的问题。

**开场约30秒。** “我们研究FlashKDA在B300上为何仍采用SM80风格MMA，分别实现了真实Phase6换指令、大chunk加rescale、value列分片。三条都通过统一对拍，A/B当前版本没有性能收益，C在H12加速1.1547倍，在H96回退。我们用控制组和硬件指标解释这些差异。”

**背景约2分钟。** 介绍KDA保存状态、逐token更新，chunk内部可矩阵化而chunk之间有依赖。再说明K1有49152份任务，K2只有96份，B300有148个SM。这给出优化动机。

**设计分析约3分钟。** 用指数和求逆反例解释C16的约束，用Phase6说明tcgen05局部有机会，同时提到TMEM和精度边界。无需在主讲时推导每条MMA编码。

**实现约4分钟。** 依次讲A为什么要物化真实U和设置HMMA控制组，B怎样用相对衰减与FP32求解绕开范围问题，C为什么能按value列独立分片。每条先说明保持了什么计算，再说改了哪一段数据流以及预期代价。

**实验约5分钟。** 先给38用例统一对拍范围，再展示三条路线的四形状完整性能。用A_control/B16限制归因，用历史C的NCU解释工作覆盖、issue与访存。不要把全部负收益归给指令代际，也不要把occupancy当成唯一目标。

**决策约1分钟。** 保留baseline；A当前集成和B当前组合实现不启用为性能后端，C保留已测H12的可选候选。未来新设计仍可检验，但当前结果不支持按架构名称统一替换。

答辩PPT每页的讲者备注已按这个节奏写好。建议15—20分钟，主讲到第22页，后面6页用于回答追问；若时间更短，可合并基础背景与NCU细节的口述。

## 13. 常见追问与可直接使用的回答

**为什么B300用SM80 MMA？** 这描述计算指令的风格。原实现围绕小tile、寄存器中间结果和逐元素更新设计，运行在B300不会自动变成新的TMEM流水线。我们通过SASS确认路径，并用实验检验替换机会。

**你们到底实现了tcgen05吗？** 实现了两个层次：先有独立Phase6实验，随后路线A把tcgen05接入完整KDA的真实Phase6，保留前五个阶段和C16算法。新SASS有UTCHMMA，38用例对拍通过，但完整forward变慢；没有宣称整个KDA的所有MMA都已换成tcgen05。

**只增加CTA不就好了？** CTA需要对应独立、完整的计算。随意增加grid会重复或错误写出。P2先证明value列可分，再修改layout和地址。它还会增加I/O成本，所以要实测。

**H96为何比H12慢？是不是候选无效？** 它在H96确实没有收益，但H12取得完整forward正收益。两个shape在GPU覆盖和重复数据成本上的权衡不同。题目允许负收益，关键是实现正确、结果可复核、解释有依据。

**能说支持所有H≤12吗？** 不能。当前只测了fixed T8192、H12等明确配置，单点不足以推出阈值或覆盖所有varlen/精度模式。

**把state接口改成FP32是否解决精度？** 原实现内部仍按BF16存储，FP32接口主要发生转换。B真正使用内部FP32 state及求解，已重新对拍和计时，误差改善伴随很大的性能成本；这和只改变API dtype是两件事。

**没有NaN为什么还不算精度通过？** 有限值也可能偏离参考很远。我们的C32求逆反例全部有限但误差约313%；完整KDA的慢写入state误差约3.77%。需要明确误差指标和应用阈值。

**共享内存减少30%为什么没有快30%？** shared memory是资源约束之一，不是时间直接占比。P2同时减少每CTA warp数、增加重复I/O。资源数字不能直接转换成加速承诺。

**为什么不能把Phase6的1.11×与C的1.1547×相乘？** 前者来自复用操作数的局部原型，后者来自完整列分片。A的完整集成已经证明局部加速不能直接外推。A与C的组合也未实现；组合会改变布局、资源和数据流，不能乘两个比值替代测量。

**负结果能证明官方永远不该出SM100专版吗？** 不能。它证明当前A/B实现没有取得收益，也支持原路径在这些形状上的工程取舍。B还不是融合SM100 kernel，A只改变Phase6。未来更好的融合和流水线可以改变结果。

**如果继续做，下一步是什么？** 当前三路线验证已经完成。进一步研究可围绕A减少U往返与同步、B融合相对衰减和求解、C验证更多实际小H工作负载。扩展由新的研究问题驱动，不为了把已有负结果改成正结果而无目的复跑。

## 14. 读完应能自己复述的核心关系

你不需要背住所有CUDA指令。先能用自己的话说明以下关系：

1. state压缩历史，同时产生时间依赖。
2. chunk把块内运算矩阵化，但块间仍需传递state。
3. GPU需要足够独立任务，也需要每个任务内部有效地调度和搬运数据。
4. A改指令也必须改数据流；B扩大chunk也扩大中间工作；C增加独立任务也复制共同读取。
5. 控制组限制归因，参考对拍约束计算，完整性能决定当前候选在已测shape上是否值得用。
